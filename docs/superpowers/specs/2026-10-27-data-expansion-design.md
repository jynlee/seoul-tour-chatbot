# 서울 장소 데이터 확장 설계

작성일: 2026-10-27 · 브랜치: `feat/data` (feat/backend de019c1에서 시작)

## 1. 왜 하나

지금 챗봇 데이터는 `data/seoul_tour.json` 574곳(종류별 약 100곳)뿐이다. 그래서 "서울 여행 친구"가 서울 여행의 기본 질문에 답하지 못한다.

- 경복궁·창덕궁 같은 대표 궁이 없다.
- 반포대교·남산서울타워 같은 야경 명소가 없다.
- 강서구 자연·휴양 장소는 1곳, 카페는 서울 전체에 14곳이라 "강서구 카페"는 다른 구 장소로 채운다(QA-9).
- 임베딩 문장에 장소 설명이 없어서 "산책"↔공원 같은 연결이 약하다.

사용자가 답을 원하는 질문(사용자 제시):
- "종로 근처 궁이나 박물관"
- "한강 야경 볼 곳"
- "기념일인데 서울 데이트 추천 코스" / "쇼핑하고 맛집 갈 건데 추천 코스" → 코스 기능은 이 작업 다음(§7).

## 2. 목표 · 하지 않을 것 · 실패로 보는 것

**목표**
- 관광공사 API(KorService2)로 서울 전체 장소를 받아 약 3,300~3,500곳으로 늘린다.
- 장소마다 개요(설명)를 받아 임베딩 문장에 넣고 `seoul-tour-v2`를 다시 색인한다.
- 상세 정보(주차·이용 시간·쉬는 날·메뉴·요금 등)도 지금처럼 받는다.
- 위 질문에서 대표 장소가 나온다(§6 확인 질문).

**하지 않을 것**
- 숙박(contenttypeid 32)은 넣지 않는다.
- 추천 코스 기능, 화면 변경, API 응답 형식 변경은 이 작업에 없다.
- 추천 점수 규칙(구 전체 관련도·주제 가산점 등)은 손대지 않는다. 데이터가 늘어서 생긴 문제만 최소로 고친다.

**실패로 보는 것 (사용자 합의)**
- 장소는 늘었는데 체인 매장·엉뚱한 곳이 앞에 나온다.
- 지금 잘 되는 맛집·카페 추천, 멀티턴(거기·다른 데 더·이름 찾기)이 나빠진다.

## 3. 범위 (사용자 확정)

| 종류 | contenttypeid | 서울 전체 수(10/26 확인) | 넣는 방식 |
|---|---|---|---|
| 관광지 | 12 | 767 | 전부 |
| 문화시설 | 14 | 579 | 전부 |
| 축제·행사 | 15 | 187 | 전부 |
| 레포츠 | 28 | 125 | 전부 |
| 음식점 | 39 | 1,590 | 전부 |
| 쇼핑 | 38 | 4,392 | **걸러서**: 시장·쇼핑 거리·백화점·면세점 위주 |

- 기존 574곳은 contentid로 합친다(같은 id면 새로 받은 목록 값으로 갱신, 기존 상세·전화 보강값은 유지).
- **기존 쇼핑 100곳에도 같은 거르기 기준을 적용한다(사용자 확정)** — '금강제화 명동본점'·'그랑핸드 가회점' 같은 개별 매장은 뺀다. 이 장소 이름에 기대는 테스트·시나리오는 반영 단계에서 고친다.
- **음식점·카페 체인은 분포를 보고 결정한다(사용자 확정)**: 목록을 받은 직후 체인으로 보이는 이름(같은 상호가 여러 지점, '○○점' 등)과 수를 뽑아 리드→사용자에게 보여 주고, 거를지 정한 뒤에 개요 받기를 시작한다(호출 낭비 방지).
- 쇼핑 거르는 기준: 먼저 서울 쇼핑 4,392곳의 cat3별 수와 예시 제목을 뽑아 리드에게 보고하고, 리드(필요하면 사용자) 확인 후 확정한다. 출발점(빌더 제안 → 확인):
  - 남김: 5일장·상설시장, 백화점, 면세점·사후면세점, 그리고 제목이 "거리·골목·상가·시장"인 곳(쇼핑 거리).
  - 뺌: 다이소·올리브영 같은 체인 지점, 개별 전문매장.

## 4. 정해진 방법

**API (리드 확인 사실)**
- 목록: `areaBasedList2`에 `lDongRegnCd=11`(서울)로 조회. `areaCode=1`은 적게 나오므로 쓰지 않는다. 종류별 `contentTypeId`로 페이지를 넘겨 받는다.
- 개요: `detailCommon2`의 `overview`. 상세: `detailIntro2`(기존 `scripts/enrich_detail.py`의 `DETAIL_FIELDS` 그대로).
- 개요·상세는 장소마다 1번씩 호출 → 하루 호출 한도 때문에 3~4일 걸린다. 한도 초과 시 멈추고 다음 날 이어 받는다(기존 `enrich_tel.py`의 `QuotaExceeded`·한 건마다 저장 방식).
- API 키는 `.env`의 `TOUR_API_KEY`만 쓴다. 커밋·로그 출력 금지(기존 `_scrub` 사용).

**파일**
- 원본 `data/seoul_tour.json`의 형식(`response.body.items.item` 목록)은 그대로 두고 내용만 합친 목록으로 바꾼다. → `app/catalog.py::load_catalog` 수정이 최소가 된다.
- 개요는 `data/seoul_tour_enriched.json`의 각 장소에 `"overview"` 필드로 넣는다(기존 `tel`·`detail`과 나란히).
- 받는 도중 상태는 중간 파일에 한 건씩 저장해서 끊겨도 이어 받는다.

**색인**
- `app/search.py::build_document_text`에 개요를 붙인다(너무 길면 앞부분만 — 길이는 빌더가 임베딩 모델 한도에 맞춰 정함).
- **새 인덱스 `seoul-tour-v3`로 만든다**(리드 결정). `seoul-tour-v2`는 574곳 코드로 도는 8000 확인 서버·팀원 서버가 계속 쓰므로 건드리지 않는다. 병합할 때 설정 기본값(`OPENSEARCH_INDEX`)을 v3로 바꾼다. `food-materials`·`seoul-tour`도 절대 건드리지 않는다(기존 `index_name_guard`에 v2 보호 추가 검토).

**받는 순서와 부분 반영 (리드 결정)**
- 호출 수 어림: 새 장소 약 2,800곳 × 2(개요+상세) + 기존 574곳 개요 ≈ 6,000~7,000건. 하루 한도에 따라 일주일 가까이 걸릴 수 있다.
- 개요가 검색(임베딩)에 들어가므로 **개요를 먼저** 다 받고, 상세는 그다음에 받는다. 개요 안에서는 관광지·문화시설 → 음식점 → 레포츠·축제·쇼핑 순.
- 개요가 다 받아지면 2단계(반영·재색인)로 넘어가도 된다. 상세는 임베딩에 안 들어가므로 나중에 받아 enriched 파일만 갱신하면 되고 재색인이 필요 없다.

**순서**
1. (지금, QA·병합과 병행) 목록 받기 → 쇼핑 cat3 분포·음식점 체인 후보 보고 → 사용자 확정 → 합친 목록 만들기 → 개요·상세 받기 시작(며칠).
   - 이 단계는 새 스크립트와 새/중간 데이터 파일만 만든다. `data/seoul_tour.json`·앱 코드는 바꾸지 않는다.
2. (main 병합이 끝난 뒤) feat/data를 main 기준으로 맞추고, 합친 데이터 반영 → 임베딩 문장 수정 → 재색인 → 테스트 기대값 정리.
3. QA가 전체 테스트 + §6 확인 질문 → 리드가 main 병합.

## 5. 데이터가 늘면서 신경 쓸 것 (빌더 판단, 결과 보고)

- 좌표가 없거나 서울 밖인 장소: 지금처럼 `has_coords`로 추천에서 빠진다. 수만 보고.
- 이름 찾기(`_match_place`·괄호 별칭): 장소가 6배가 되면 짧은 이름이 일상 말과 겹칠 수 있다(예: "공원", "카페" 같은 제목). 겹치는 제목 목록을 뽑아 보고하고, 기존 짧은 이름 규칙으로 막히는지 확인.
- 같은 장소가 두 번(같은 이름·거의 같은 좌표, 다른 id): 수를 보고하고 하나만 남기는 규칙을 제안.
- 통합 테스트·화면 스크립트 중 574곳 데이터에 기대는 것(특정 장소 이름, "강서구 카페 없음" 등)은 데이터 반영 단계에서 기대값을 고친다. 단위 테스트는 가짜 카탈로그를 쓰므로 영향이 적을 것으로 본다.
- 응답 속도: 장소 수가 늘어도 한 번 질문에 걸리는 시간이 눈에 띄게 늘지 않는지 확인.

## 6. 끝났다고 보는 기준

- 데이터: 서울 약 3,300~3,500곳, 개요가 있는 장소 비율과 상세 항목별 수를 보고.
- 확인 질문(8000이 아닌 팀원 포트에서 실서버로):
  - "종로 근처 궁이나 박물관" → 경복궁·창덕궁 등 궁, 박물관이 나온다.
  - "한강 야경 볼 곳" → 반포대교·한강공원 같은 야경 명소가 나온다.
  - "강서구에 산책할만한 곳" → 공원·습지 같은 자연 장소가 앞에 나온다.
  - "강서구 카페 추천해줘" → 강서구 안 카페가 먼저 나온다(구 안이 3곳 미만이면 다른 구로 채우는 지금 규칙(QA-9)은 그대로 둠 — 리드 결정).
  - "명동 쇼핑할 곳" → 체인 지점이 아니라 시장·쇼핑 거리·백화점이 나온다.
  - 기존 맛집·카페·멀티턴 시나리오(manual-qa) 그대로 통과.
- 단위·통합·JS·화면 테스트 전체 통과.

## 7. 다음 작업 (이 문서 범위 밖)

"추천 코스" 기능 — 데이터 확장이 끝난 뒤 별도 설계(사용자 확정 순서).

## 8. 리드가 정한 것 (사용자 확인용)

- 작업 브랜치를 feat/backend 최신(de019c1)에서 만든 `feat/data`로 함. 데이터 받기는 앱 코드를 안 건드리므로 지금 QA·병합과 충돌하지 않음.
- 원본 파일 형식을 유지하고 개요는 enriched 파일에 넣음(코드 변경 최소).
- 쇼핑 거르는 정확한 기준은 실제 cat3 분포를 보고 확정(위 출발점에서 크게 벗어나면 사용자에게 다시 물음).
- 축제·행사는 지난 행사도 일단 전부 넣음(지금 동작과 같음). 날짜로 거르는 건 나중 과제.
